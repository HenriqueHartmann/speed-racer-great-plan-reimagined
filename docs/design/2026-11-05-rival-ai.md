# Design — the rivals

**Status:** draft, for review. Not approved.
**Date:** 2026-11-05
**Source:** `019_BehaviorScript_26_-_doEnemy.ls` (879 lines), `006_…_PREP.ls`,
`000_…_MOVIE.ls`, and `public/models/track.glb`.

Make it a race. The level is complete but for its rivals: the course, the
fences, the trees, the pickups, the water and the sky are all in, and the one
thing `doEnemy` was written to do — put cars in front of the player — has never
been attempted.

**Evidence taxonomy**, unchanged from `2026-11-05-original-track.md`:
CONFIRMED (shown by the source or by a repeatable measurement), SUPPORTED
(everything converges, nothing contradicts), UNRESOLVED (recorded, not guessed).
Implementation constants keep the existing RECOVERED / SUBSTITUTE tags.

---

## The headline, because it changes what gets built

**The original never has nineteen cars on the track.** `PREP:49-52` sets
`enemiesRemaining = 19` and `enemyPositionsList = [0, 0, 0]`, and `PREP:459-466`
drives the whole field with `sendSprite(2, …)`. Sprite 2 carries the Mach 5's
behaviour and **three** `doEnemy` instances, each with its own
`pStartingPathStep` sprite property (`doEnemy:866-878`).

Three cars, recycled nineteen times. When a rival falls 40 units behind the
player it is teleported back in front of the leader with a fresh skin and a
fresh damage count (`doEnemy:236-321`, `doJump`), and `enemiesRemaining` drops
by one. The player starts 20th (`gPosition = enemiesRemaining + 1`) and climbs
by passing the same three cars over and over.

This is the single most important recovered fact in the whole script, and it is
what makes rivals affordable: the simulation carries three vehicles, not
nineteen. (CONFIRMED.)

## What the racing line actually is

209 nodes named `path_01`…`path_209` in `track.glb`. Measured, all 209 present,
none carrying rotation or scale:

| | |
|---|---|
| Span | x −97.5…293.6, y 35.3…11084.9, z −7.1…29.1 |
| First / last | (49.3, 35.3, 16.0) / (6.5, 11084.9, 16.0) |
| Y monotonicity | **208 of 208 steps increase** — the line never doubles back |
| Spacing | min 21.45, p50 62.10, p95 90.23, max 105.61 |

`PREP:308-311` quantises them on load:

```
pntLoc = point(integer(x), integer(y))
pathList[pntNum] = [pntLoc, 0, ceil(z)]
```

So the stored line is **integer x and y** (Lingo's `integer()` rounds — proved
in the track design from `MOVIE.ls:263-288`) with a ceiling-rounded z, and the
nodes are then removed from the world. Three consequences:

1. **The AI steers in 2D.** Only `[1]` (the point) is read while driving; the z
   is read only when a car is placed or replaced.
2. The strict Y monotonicity is why `tYOffset = rivalY − playerY` works as the
   race-position measure throughout the script. It is a property of this level's
   line, not a general truth, and the code depends on it.
3. The acceptance radius is 10 (`goto_dist < 10`, `doEnemy:424`) against a
   median spacing of 62. A car therefore aims at a point it will overshoot
   rather than circle. (All CONFIRMED.)

## How a rival drives

`doEnemy:369-560`. It is the Mach 5's own chassis loop with the keyboard
replaced by a pursuit controller, and most of it is code we already have.

### Shared with the Mach 5, verbatim

The suspension is the same four-wheel ray spring — same `modelsUnderRay` with
`#maxDistance: 1`, same two-segment seam rule, same
`f = −pStrength·(pHoverDist − d) − pDamping·(v·diff)` — the same
`powerCoeff = grounded/4`, the same sideways-grip impulse, the same
self-righting block when `powerCoeff = 0`, the same visual wheel turn and spin.
`doEnemy` differs from `doMach5` in exactly one respect here, and it matters for
drawing: it has **no `else` branch** writing `pHoverDistList[i] = pHoverDist`
when a wheel misses, so a rival's loose wheel keeps its last grounded distance,
where the Mach 5's snaps to 1.2 (`doMach5:474, 480`). It also omits the
`max(0.75, …)` floor on the drawn drop. (CONFIRMED.)

### Its own constants

| Property | Rival | Mach 5 | Note |
|---|---|---|---|
| `pCarMass` | **20000** | 30000 | the rival is lighter |
| `pAccGain` | 0.07 | 0.07 | both overwritten in `prepareCar` |
| `pDecGain` | 0.04 | 0.04 | |
| `pStrength` / `pDamping` | 3.0 / 0.05 | 3.0 / 0.05 | |
| `pHoverDist` | 1.2 | 1.2 | |
| `pwidth`, wheelbases | 1.55, 1.2, 1.2 | same | |
| `pMaxSpeed` at `beginSprite` | `gM5MaxSpeed · 0.8` | 69 | then overwritten every tick |

### Steering: angular impulse toward the next point

```
goto_rot  = −getAngle(cur.x, cur.y, next.x, next.y)
goto_dist = |cur − next| in the XY plane
dif       = goto_rot − chassisRotation.z     (wrapped into ±180)
turnFactor = min(40, |dif|) / 40
distFactor = 1 − min(50, goto_dist) / 50
applyAngularImpulse( ±mass·turnFactor  −  0.25·angularMomentum.z )
```

Note what is **absent**: no brake, no speed-dependent steering limit, no
lookahead beyond one point. Cornering is handled entirely by the speed rule
below, which multiplies the target speed down by `turnFactor · distFactor` —
the car slows when it is both badly aimed and close to its target.

The `±180` wrap has a real bug in it (`doEnemy:449-453`): the `dif > 180` branch
computes `180 − dif`, where the symmetric correction is `dif − 360`. For
`dif = 190` the original yields −10 instead of −170, so a car needing a large
left turn is told to make a small one. Whether to port the bug is a decision
below. (CONFIRMED by reading; its effect is UNRESOLVED until measured.)

### Throttle: there is only full throttle

```
imp = (pMaxSpeed − forwardVel) · pAccGain · mass · worldForward · powerCoeff
```

every tick while `pIsReady` and `isPlaying`. The rival never lifts. All of the
racecraft lives in `pMaxSpeed`, which is rewritten at the end of every tick.

### Rubber-banding: `pMaxSpeed` is a function of where the player is

`doEnemy:725-806`, driven by `tYOffset = rivalY − playerY` and by `pSmartEnemy`,
which is cleared when the rival is rear-ended by another rival. For an ordinary
rival (`isDuggary = 0`), against `gM5MaxSpeed` — the player's own top speed,
republished every tick by `doMach5:51`:

| Condition | `pPassMODE` | Target before the turn penalty |
|---|---|---|
| `pSmartEnemy = 0` | 2 | `0.60 · gM5MaxSpeed` |
| ahead of the player (`tYOffset < 1`), within a random 100–200-tick window | 1 | `1.03 · gM5MaxSpeed` |
| otherwise | 0 | `0.73 · gM5MaxSpeed` |

Then `pMaxSpeed = ts − ts · turnFactor · distFactor` in every branch.

So a rival the player is catching gets a **3% advantage for one to three and a
half seconds**, then drops to 73% and is passed. Being hit from behind by
another rival drops it to 60% permanently until it is recycled. The window is
re-rolled — `pSmartTIMER = the ticks + random(100) + 100` — each time the car
goes from behind to ahead. (CONFIRMED.)

### The Duggary is a different car

When `enemiesRemaining` reaches 1, the next recycled rival becomes the Duggary
(`doEnemy:303-309`): the boss. It is never removed from the world, it has its
own five-way `pPassMODE` table reaching `1.3 · gM5MaxSpeed`, it triggers a music
change and voice-over when the player first comes within 30 units, it is immune
to damage and to the Robot, and it has stuck-detection — five seconds without
gaining 2 units of Y, or falling below z = −30, and `doResetDuggary` walks the
path list to the player's own Y and teleports it back alongside.

### Dying, and the Robot

`collisionHandler` (`doEnemy:161-234`) keeps `userData.damage` per rival:

| Hit | Damage | Note |
|---|---|---|
| rear-ended by another rival | `hitforce · 0.5` | only the car in front takes it; also sets `pSmartEnemy = 0` |
| the player, Blades up | **15** | |
| the player, otherwise | **2.5** | |
| `solid` or `tree`, `hitforce > 10` | **100** — instant | at most once a second |

At 30 the car starts smoking (`explosionMODE = 1`); at 100 it explodes
(`explosionMODE = 5`), which scores the player **1000** and recycles it.
A rival hit by the Mach 5's Robot has `controlMODE` set to 0 by
`doMach5:548`; it then spins helplessly for 0.4 s, and **any** collision while
`controlMODE = 0` detonates it. That is the Robot's whole purpose and it is
already half-built on our side: `pickup_Robot` rearms the gadget, and nothing
has ever been a target. (CONFIRMED.)

### Finishing and position

`gPosition` moves by one whenever a rival crosses the player in Y, in either
direction, with a passing sound when |Δx| ≤ 10. A rival that runs off the end of
the path list increments `enemiesFinished` and is removed. The player's own
finish is elsewhere (`handlePickups:161`, `PLAY:114`), already keyed on
`gPosition = 1`.

## Goals

1. Three rival cars drive the recovered racing line, deterministically, inside
   `src/sim/`.
2. The recycle-and-renumber system, so twenty places exist with three cars.
3. `gPosition` moves as the original moves it, and the existing finish rules
   become reachable.
4. Rivals are solid: they collide with the player, with each other, and with
   the course, and they take and deal the recovered damage.
5. The Robot gadget gets its target.

## Non-goals

- The Duggary's music, voice-over and skin rotation. The behaviour is in scope;
  the presentation is not, because the project has no audio at all yet.
- Explosion, smoke and debris particles. The *state machine* is in scope so the
  car dies and recycles correctly; the particles are a renderer task.
- Any second or third level.

## Anti-goals

- **A better racing line.** The 209 points are the original's and are used as
  stored, integer-quantised.
- **A better driver.** No brake, no lookahead, no racing-line optimisation. The
  original is a pursuit controller with a rubber band and the fidelity is the
  point.
- **`Math.random()` anywhere.** The original rolls dice in five places
  (`pSmartTIMER`, the Duggary's speed, skin choice, the ±1 jitter on a recycled
  car's target, voice-over selection). Every one of them must come from the
  World's existing seed, or replays stop being replays.

## The design

### Where it lives

`src/sim/rival.ts` — a `Rival` with the pursuit controller, the speed table and
the damage rules, driven by the same fixed timestep, holding no renderer
reference. `src/sim/race.ts` or an extension of `World` owns the three of them,
`enemiesRemaining`, `enemyPositionsList` and `gPosition`.

The racing line becomes a fourth decoded asset, `track-path.bin`, built by a new
`tools/build_track_path.mjs` following `parseGroundMesh`'s conventions exactly
and plugged into `tools/extract_mesh.sh` as step 8. It stores the quantised
`[integer(x), integer(y), ceil(z)]` that `PREP` stores, not the raw float — the
quantisation is part of the behaviour, not a detail of the loader.

### Reuse, not duplication

A rival's chassis loop is the Mach 5's. `src/sim/vehicle.ts` already holds it,
parameterised by constants rather than by a vehicle object; the work is to
thread the four values that differ (mass, and the three drawing differences
noted above) rather than to write a second integrator. **How far that
refactoring should go is the main open question for review**: a shared
`stepChassis` taking a parameter block is the obvious shape, and it touches the
one file in the project with the most tests behind it.

### Physics

Each rival gets a Rapier dynamic body, as the player has. They are *movable*
rigid bodies in the original (`makeMovableRigidBody(name, 20000, 1, #box)`) with
`friction = 0`, and they carry the same per-segment collision toggling the
player does, through `doEnemyChangeSegment` — which is `doM5ChangeSegment` with
the same two bugs `MOVIE.ls` has for the player. We did not port those bugs for
the player and will not port them here.

### Determinism

`World` already carries a seed and `src/sim/` is already free of `Math.random()`.
Every rival draw comes from that stream. The ordering of the three rivals'
updates is fixed and part of the contract; the replay test must cover a run long
enough for at least one recycle.

## Calls I would make, for review

**Port the `±180` wrap bug.** `180 − dif` is wrong and the correct line is
`dif − 360`, but it fires only for turns sharper than 180° of error, which on a
monotone line happens when a car is spun around — exactly the `controlMODE = 0`
and post-recycle cases. It is recovered behaviour, it is cheap, and the
alternative is a rival that recovers from a spin more gracefully than the
original's did. Tag it RECOVERED with the arithmetic spelled out, as the brake
and `TURN_BUILD_FLOOR` are.

**Three rivals, not a configurable number.** `enemyPositionsList = [0, 0, 0]` is
the evidence and nineteen is a count, not a field size.

**Model `explosionMODE` as simulation state, draw nothing.** The state machine
governs when a car is removed, when it is recycled and when the player scores
1000. Those are rules. The particles are not.

**Leave `pStartingPathStep` UNRESOLVED and substitute.** The three starting
offsets are Director sprite properties, stored in the binary score, not in any
decompiled script. They are not recoverable from the Lingo. Substitute three
evenly spaced steps ahead of the player, tag them SUBSTITUTE, and record what
they would have to be read from.

## Left to the builder

- The exact shape of the shared chassis step.
- Whether the three rivals update before or after the player within a tick. The
  original's sprite order decides it and the score is binary; pick one, state it,
  and pin it with a test.
- The binary layout of `track-path.bin`.

## Risks

**The one that would sink it:** three extra dynamic bodies and their twelve
suspension rays per tick, against a ground probe that scans the active
segment's triangles by index. Rivals multiply that probe by four. Whether it is
already the dominant cost is **unmeasured** — the project has never profiled a
frame, which is why performance is an open item in its own right. *Measure the
probe before Pass 1, not after.* If it does not hold, the fix is a spatial index
on the ground mesh: known, bounded, and worth doing on its own merits.

**The one that is only unpleasant:** `vehicle.ts` carries the most tests in the
project. Refactoring it to serve two vehicles risks a silent change to the
player's handling. Every step of that refactoring must leave the existing
suite green with no edits to its assertions.

## Unresolved, recorded rather than guessed

- The three `pStartingPathStep` values.
- The sprite update order within a frame.
- `gHavok.makeMovableRigidBody(name, mass, 1, #box)` — the third argument, as
  for every other Havok call in this project.
- Whether `distFactor`'s 50-unit scale was tuned against the median 62-unit
  waypoint spacing or is a coincidence.
